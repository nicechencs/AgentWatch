# ADR-0003 本地存储采用 SQLite（WAL）

> 状态：已接受
> 最后更新：2026-10-06
> 关联：REQ-05、REQ-07、NFR-03、SPIKE-06、ADR-0011

## 背景

需要在本地持久化会话数据，支持筛选、聚合和导出；不引入额外服务，磁盘占用可控。

## 决策

- 使用 `rusqlite`（bundled，静态链接 SQLite）。配置：WAL 模式、`synchronous=NORMAL`、`page_size` 使用默认值。
- **单写线程**：管道按批（100 ms 或 1000 条）在一个事务里写入。查询使用独立的只读连接池。
- 每个安装只有一个数据库文件，按 `session_id` 分区。保留策略以整个会话为单位清理，清理后做增量的 `VACUUM`（启用 `auto_vacuum=INCREMENTAL`）。
- 表结构和迁移见 [storage.md](../01-architecture/storage.md)。迁移使用嵌入代码的 SQL 脚本，版本号记录在 `schema_meta` 表。

## 备选方案

| 方案 | 不选的原因 |
|---|---|
| DuckDB | 分析查询强，但二进制大（约 +20 MB），并发写入模型不适合持续写入。以后可以作为导出分析工具引入 |
| 纯 JSONL 文件 + 索引 | 筛选和聚合要自己实现；但可以作为导出格式和调试用的原始流 |
| sled / redb（KV） | 没有查询语言，筛选要自己写 |
| Parquet 分段 | 写入延迟高，实时查询差 |

## 后果

- 正面：零运维；用户可以直接用 sqlite3 审查数据；AI 写 SQL 很熟练。
- 代价：高事件率下写入会成为瓶颈，所以必须先聚合（ADR-0011）。默认不加密，靠文件权限保护。
- 跟进：SPIKE-06 测量持续写入吞吐和查询延迟。

## 重新评估的触发条件

- 聚合后的写入仍超过每秒 2 万行，或者主要查询超过 300 ms。
