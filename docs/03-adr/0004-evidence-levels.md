# ADR-0004 所有记录携带证据等级，关联只产生推测

> 状态：已接受
> 最后更新：2026-10-06
> 关联：REQ-06、[evidence-model](../01-architecture/evidence-model.md)

## 背景

审计工具最危险的错误是**把推测当事实**，例如“读了 `.env` 之后有外发流量”被说成“上传了 `.env`”。另外，各平台的采集能力差别很大，同一个字段在不同平台上可信程度也不同。

## 决策

1. `RawEvent` 和所有落库记录都必须有 `evidence`（E1/E2/E3/S/I/NA）和 `source`（格式为「采集器/子源」，如 `linux.ebpf/tcp_sendmsg`）字段。这在类型层面强制：构造函数里必须传入。
2. 字段级的 NA：字段本身用 `Option<T>`，另用 `field_evidence: {字段路径 → Evidence}` 记录与记录级不同的字段证据；不可得时写 `NA(reason)`。规则是“`None` 且 `field_evidence` 中没有该字段”的情况只允许出现在语义上本就可空的字段上，由采集器检查清单和回放测试保证。这样“没采到”和“值为空”可以区分开，序列化也更紧凑。详见 [event-schema](../01-architecture/event-schema.md) 与 [evidence-model §2.1](../01-architecture/evidence-model.md)。
   - 曾考虑的 `Field<T> = Known(T) | Unavailable(Reason)` 包装类型，因为会让所有字段访问和 serde 都变复杂而放弃。
3. 关联引擎只能产生 `evidence=I` 的 `finding`；措辞必须来自 evidence-model 中定义的模板。单元测试会断言输出里不含禁用词，如“上传了文件”“泄露了”。
4. 只有一种情况可以升级为“内容匹配证据”（E2）：代理模式下的分块哈希匹配（CAP-URL-04）。
5. E3（Agent 自报告）可以用来标注和对照，但**不能**单独支撑任何 finding。

## 备选方案

| 方案 | 不选的原因 |
|---|---|
| 用置信度分数（0–1） | 用户无法理解 0.7 是什么意思；算法一改，含义就变 |
| 不区分等级，只在文档里说明 | 用户看不到；导出之后信息就丢了 |

## 后果

- 正面：导出、UI、CLI 的语义一致；满足 REQ-06。
- 代价：每条记录多两个字段（在存储里用字典编码的小整数表示）；采集器开发者必须给每个字段定下等级。

## 重新评估的触发条件

- 出现新的证据来源，而现有等级无法表达。
