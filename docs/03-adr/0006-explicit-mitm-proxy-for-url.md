# ADR-0006 完整 URL 通过显式 MITM 代理获取

> 状态：已接受
> 最后更新：2026-10-06
> 关联：REQ-04.4、REQ-06.3、REQ-07、CAP-URL-01、SPIKE-04

## 背景

外发流量绝大多数是 HTTPS，内核层和网络层都看不到 URL。要拿到 URL，只有三条路：中间人代理、TLS 库 hook（只有 Linux uprobe 可行）、各网络栈自带的遥测（覆盖面窄）。

## 决策

- `aw-proxy` 基于 `hudsucker` 和 `rcgen`，只在**启动模式且用户显式加上 `--proxy`** 时启用。
- 注入方式：只给被启动的进程树设置环境变量：
  - `HTTPS_PROXY`/`HTTP_PROXY`（大小写两种写法都设）、`NO_PROXY`；
  - `NODE_EXTRA_CA_CERTS`、`SSL_CERT_FILE`、`REQUESTS_CA_BUNDLE`、`CURL_CA_BUNDLE`、`GIT_SSL_CAINFO`【完整清单待 SPIKE-04 确定】。
  - CA bundle 的生成方式：系统根证书加上 AgentWatch 的 CA。否则 `SSL_CERT_FILE` 会把系统根证书覆盖掉。
- CA 证书在安装时生成，每台机器唯一。私钥只有 daemon 可读。**不装入系统信任库**。卸载时删除。
- 代理只记录：方法、完整 URL（脱敏后）、状态码、请求和响应 body 的字节数、内容类型、耗时。body 只在内存中按分块算哈希，用于 CAP-URL-04，**不落盘**。
- 客户端与代理之间的连接用连接的源端口归属到 PID（由内核采集器提供），从而把 URL 和进程对应起来。
- 代理的上游连接以 daemon 的身份发出，归属需要特殊处理：标为“经代理”，并把字节数算回原进程，避免重复计数。详见 network-attribution。
- 不经过代理的连接一律标成“直连”。比如程序不认环境变量、走 QUIC、做了证书固定导致握手失败。
- 有些域名可以配置成“不解密、只透传”：默认包括银行和密码管理器；用户也可以自定义。

## 备选方案

| 方案 | 结论 |
|---|---|
| 透明代理（iptables/WFP/pf 重定向） | 还是绕不开 CA 信任的问题，而且会影响全系统；以后作为可选功能再评估 |
| 把 CA 装入系统信任库 | 影响范围太大，安全风险高。不选 |
| 只用 TLS uprobe | 只有 Linux 支持，而且覆盖不全。作为补充（CAP-URL-02） |
| 使用 mitmproxy 外部进程 | 需要 Python 运行时，体积大。不选，但实现时可以参考它 |

## 后果

- 正面：三平台一致的 E2 级 URL；也是“内容匹配证据”的唯一来源。
- 代价：只对认代理环境变量的程序有效；代理会增加延迟；引入 CA 私钥这一敏感资产。
- 跟进：SPIKE-04 确认各运行时是否认可这些变量；在 security-privacy 中写清 CA 的生命周期。

## 重新评估的触发条件

- 主流 Agent 的 HTTP 客户端不认环境变量，导致代理覆盖率低于 70%。
