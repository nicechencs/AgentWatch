# ADR-0014 启动模式下提供可选的拦截与改写

> 状态：提议
> 最后更新：2026-10-21
> 关联：REQ-09、REQ-10、REQ-12、ADR-0006、ADR-0008、ADR-0012、SPIKE-07、SPIKE-09、[拦截方案](../proposals/aw-intercept-design.md)

## 背景

原来的产品决定是「只审计、不拦截」（requirements §3、vision §4），`aw hook` 故意从不返回 deny（`crates/aw-cli/src/cmd/hook.rs:3-5`）。2026-10-21 用户决定要做拦截，并评估内容替换。Claude Code 和 Codex 的官方 hook 都已支持「拒绝」和「改写工具参数」，`aw run` 又是启动者，可以在本次启动里装好关卡而不改用户配置。

## 决策

1. 在 `aw run` 启动的会话里提供**可选**拦截：动作是放行、拒绝、改写、问用户；规则缺省关闭，关闭时行为与现在一致。
2. 第一步只用三层：agent 自带 hook、`aw mcp-tap`、会话网络代理（代理第一步只拒绝、不改写）。系统层（Linux Landlock/seccomp）放第二步；macOS ES AUTH 等授权；Windows 不做驱动（维持 ADR-0008）。
3. 判定在 `aw hook` / `aw mcp-tap` / 代理进程本地完成，不依赖后台在线。
4. 每次拒绝、改写、问用户都写审计：脱敏摘要 + 加盐哈希，不存原文（维持 ADR-0012）。
5. 新增审计存储（迁移 `0012_intercept_events.sql`）和后台路由 `POST /api/v1/agent/intercept`。

## 备选方案

| 方案 | 优点 | 缺点 | 不选的原因 |
|---|---|---|---|
| 维持只审计 | 简单、无误伤 | 用户明确要拦截 | 用户已决定 |
| 规则在后台判定 | 规则集中、好管理 | 后台不在就没法判；hook 有时间预算 | 可用性差 |
| 第一步就做系统层 | 绕不过 | 三系统差异大，Mac 要授权，Windows 要驱动 | 成本高，先做三系统都能做的 |
| 代理改写模型 API 流量 | 能力最强 | 卡流式输出、风险高、审计难诚实 | 第一步不做 |

## 后果

- 正面：用户能挡住危险命令、强制改参数；三系统同一套规则。
- 负面 / 代价：第一到三层都是「软」拦截，agent 有管理员权限或刻意绕过时管不住；Codex hook 出错时可能放行；误伤风险。
- 需要跟进：requirements / vision 已同步改写；P5-AGENT-02「限制」改写；新任务卡 P5-SEC-01～04；Codex 注入方式真机验证；第二步 Linux 兜底 ADR。

## 重新评估的触发条件

- Claude Code 或 Codex 的 hook 决策格式有不兼容变化。
- 真机验证发现 hook 注入在某平台不可用。
- 苹果 ES 授权批下来（可评估 macOS 系统层）。
