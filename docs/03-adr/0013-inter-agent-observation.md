# ADR-0013 以通道为事实、协议为增强的 Agent 间通信观测

> 状态：提议
> 最后更新：2026-10-07
> 关联：REQ-11, CAP-IPC, SPIKE-09, ADR-0004, ADR-0006, ADR-0012

## 背景

用户需要同时监控多个 Agent 之间的通信：父子派生、MCP server 调用、本机 IPC、共享文件、跨主机协议。现有设计只记录 Unix socket 和命名管道的连接动作（CAP-NET-06），没有两端配对和字节数，也没有“Agent 实例”这一概念。协议内容里常有提示词和凭证，隐私风险高。

## 决策

1. **通道是事实**：在内核或系统层配对本机 IPC 的两端进程并统计字节（E1），只对跨 AgentInstance 的通道做按字节计数，在内核侧过滤。
2. **协议是增强**：MCP / A2A 等协议元数据（E2）只通过**显式、可见的拦截点**获取——启动模式下的 `mcp-tap` stdio 包装器和现有代理；不默认读取 IPC 内容。
3. **只存元数据**：method、工具名、参数形状、字节数、耗时。内容只用于本地分块哈希比对，不落盘（与 ADR-0012 一致）。
4. **Agent 身份是判断**：AgentInstance 的识别本身带证据等级，规则匹配为 I。
5. **链路取最弱一跳**：委托链路的结论等级取各跳中最弱的一级；共享文件关联永远是 I。
6. **多会话用监控组**：独立启动的多个 Agent 通过 `watch_groups` 组合，而不是让单个会话包含多个根。
7. **跨主机只做离线合并**（1.0 范围内），不做实时集中式采集。

## 备选方案

| 方案 | 优点 | 缺点 | 不选的原因 |
|---|---|---|---|
| 默认用 eBPF / ETW 读取所有 IPC 内容做协议解析 | 无需包装器，附着模式也能用 | 仅 Linux 可行；开销高；在内核层读取提示词与凭证，隐私风险大 | 只作为 Linux 可选功能，默认关闭 |
| 修改用户的 MCP 配置文件，插入包装器 | 覆盖面广 | 污染用户配置；崩溃时可能无法还原 | 只在启动模式下用临时配置 |
| 只用 Agent 自报告（E3） | 实现简单 | 不可信、不完整 | E3 不能单独支撑结论（ADR-0004） |
| 实时多机汇聚 | 跨主机链路完整 | 需要服务端、鉴权、网络传输，超出 1.0 范围 | 先做离线合并 |

## 后果

- 正面：给出可信的“谁和谁通信、传了多少”，并把 MCP 工具调用与 server 的实际行为对齐。
- 负面：附着模式和未启用 tap 时看不到工具名；macOS 上 IPC 字节数可能长期为 NA。
- 跟进：SPIKE-09；P6 任务；在 capability-matrix 中新增 CAP-IPC，并把 CAP-NET-06 标为由 CAP-IPC 补充。

## 重新评估的触发条件

- 主流 Agent 提供稳定的 MCP 审计日志或 OTEL 语义约定，可以替代包装器时。
- 用户普遍需要实时跨主机链路时。
