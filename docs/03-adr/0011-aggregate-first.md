# ADR-0011 采集端先聚合再存储

> 状态：已接受
> 最后更新：2026-10-06
> 关联：NFR-01~03、ADR-0003、[pipeline](../01-architecture/pipeline.md)

## 背景

Agent 的一次会话可能包含 `npm install` 或全仓库搜索，单条读写事件可能有数百万条。逐条存储会违反磁盘和 CPU 预算，而且对审计并无必要。

## 决策

- **文件**：一个句柄从 open 到 close 的生命周期聚合成一条 `file_access`，内容包括读次数、读字节数、写次数、写字节数、首末时间。长期不关闭的句柄每 30 s 刷新一次快照。
- **网络**：每条连接一条 `net_flows`，另外按 5 s 时间桶写 `net_flow_buckets`，用于画时间线上的流量曲线。
- **噪声折叠**：同一进程在 1 s 内对同一目录下大量只读的 open（如加载依赖），可以折叠成一条“目录批量访问”记录，带上文件数和前 N 个样例。**命中敏感路径规则的永不折叠**。
- 聚合尽量放在最靠近源头的地方：Linux 在内核中做，Windows 和 macOS 在采集器回调里做。
- 调试模式 `--raw` 会把未聚合的原始事件另写到 JSONL 文件，并有大小上限。

## 备选方案

| 方案 | 结论 |
|---|---|
| 逐条存储，查询时再聚合 | 磁盘占用和写入开销不可接受 |
| 采样 | 会丢失审计关心的个别事件 |

## 后果

- 正面：稳定达到 NFR-03 的磁盘预算。
- 代价：丢失单次读写的精确时间和偏移量；一个句柄内的读写顺序不可见。关联引擎必须使用时间区间，而不是时间点。
